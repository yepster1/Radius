01

The reframe

RentEngine sells to property managers filling vacancies — not to home buyers. That single fact should shape every card on the page. Same underlying data, a much more relevant answer, and it quietly demonstrates you researched who you're building for.

Generic take

“Insights about an address”

Is this a good place to live?

Walk score, some nearby pins, a map. Reads like every other geo-API demo. Nothing about it says the builder thought about who would use it or why.

RentEngine take

“Who do I market this unit to?”

Which renter does this address win, and what do I put in the ad?

Identical data, aimed at a leasing decision. Persona fit, flags a prospect will raise on a viewing, and the three amenities worth naming in the listing. Directly serves their “fill vacancies 9 days faster” pitch.

Product direction

Answered · A

Three coherent versions of the same brief. They differ in what the page is for, which changes the layout and which cards earn their place. Pick one — everything downstream follows.

  • Report opens with Renter Fit — which persona this address wins
  • Flags framed as viewing objections + selling points
  • Ends with three listing angles drawn from the top signals
  • Scores support the narrative rather than lead it
Why: speaks RentEngine's language. Cost: persona weights need defending — a reviewer will ask how you chose them.
  • Scores lead: walk / transit / drive / errand
  • Dense charts, demographics, POI breakdowns
  • Neutral — works for buyers, renters, agents alike
  • No interpretation layer to defend
Why: safest, most obviously "complete". Cost: it's the expected answer. Shows competence, not insight.
  • Full-bleed map that flies between points as you scroll
  • Insights revealed as narrative beats
  • Highest visual wow-factor
  • Beautiful shareable artifact
Why: most memorable. Cost: slow to scan, weak on mobile, and reads as a portfolio piece rather than a product.

Which direction?

My recommendation is A — it's the only one that answers a question RentEngine actually has. B's depth survives inside A: the scores are all still there, just positioned as evidence rather than the headline.

06

How the scores are computed

Anyone can print a number an API handed them. Computing it from raw OSM geometry, with a documented and inspectable formula, is the part that reads as engineering. This ships as a real page in the app.

# Walk Score — distance-decayed amenity access for each of 9 categories (grocery, dining, cafe, retail, errands, parks, schools, culture, fitness): nearest = closest 1–3 amenities within 2000 m walking distance decay(d) = e^( -5 · (d / 2400)^5 ) # same curve Walk Score uses category_score = Σ decay(dᵢ) · position_weight(i) raw = Σ category_score · category_weight penalty = f(intersection_density, avg_block_length) # grid beats cul-de-sac WalkScore = clamp( raw · (1 − penalty), 0, 100 )

Every other score follows the same shape — a stated input set, a stated transform, a clamped output. The /methodology page renders these formulas next to the live values for the address you're viewing, so the number and its derivation sit side by side.

08

Risks I'm tracking

Named now so they don't surprise us mid-build. None are blockers; all shape the plan.

Overpass API is slow and rate-limited

Public endpoints take 2–10 s and throttle aggressively. A cold report could feel broken. Mitigation: cache aggressively at the edge keyed by rounded coordinates, run categories in parallel, stream results into the page so scores appear as they resolve rather than all at once.

OSM coverage is uneven

Dense US cities are excellent; rural areas are sparse. A rural address may score 12 and look broken when it is simply accurate. Mitigation: detect low data density and say so explicitly on the card rather than showing a bare low number.

Mapbox tokens are public by necessity

The GL JS token ships to the browser. Mitigation: URL-restrict the public token to the Vercel domain, keep a separate secret token server-side for Search Box and Isochrone calls, proxy those through route handlers.

Persona weights are subjective

The most interesting feature is also the most arguable. Mitigation: publish the weights, let the methodology page show exactly which inputs drove each score, and frame them as a defensible model rather than a truth claim. Own it visibly instead of hiding it.
